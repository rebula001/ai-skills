# Dependabot PR Review

## 使用范围

- “请查看 Dependabot PR”：检查当前指定或上下文明确的仓库中的开放 Dependabot PR；只有一个时分析它，存在多个时先列出并由用户选择，未找到时说明结果。
- 用户指定某个 Dependabot PR 并要求检查、分析或验证时，处理指定的 PR。
- 仅要求列出 PR 时，列出状态并等待用户选择；不要自动分析或合并所有 PR。本 skill 不替代项目的开发、验证和提交规则。

## 检查与分析

1. 确认目标仓库、PR 和基准分支；未指定时根据上下文识别，存在歧义时询问。通过 GitHub CLI 或可用的 GitHub 工具读取 PR 状态、来源、head commit、变更文件、检查结果，以及关联的 Dependabot 提醒。获取不到的信息如实说明，不猜测。
2. 检查实际差异与依赖链：区分直接和间接依赖、运行时和开发依赖，列出受影响版本、变更范围和重大版本升级。对安全更新，核对漏洞编号、严重性、受影响范围、修复版本及项目实际暴露路径；不能因依赖仅用于开发就认定没有风险。对普通版本更新，说明其目的。
3. 核对更新及新增依赖的许可证、Node 和其他运行环境要求、项目固定版本约束及兼容性。区分许可证标识检查与完整发行义务审核；如有未知项或项目要求的确认关口，明确说明。
4. 根据风险验证精确的 PR head，优先在独立临时目录或隔离检出中安装锁文件对应的依赖，按需运行类型检查、lint、测试和构建；涉及用户交互或数据安全时补充相应验证。不得覆盖现有工作区或用户数据；说明验证环境、运行结果、失败和未覆盖范围。无法执行时说明原因，不将推测写成测试通过。

## 结论与合并

- 给出 PR 链接、变更摘要、漏洞与影响、许可证和兼容性、验证证据及剩余风险，并建议合并、补充检查或暂缓。明确报告仍有其他漏洞或检查未完成的情况。
- 检查或分析不等于授权合并、评论、关闭、修改 PR 或推送。仅在用户明确要求合并后执行；合并前重新核对目标分支、工作区及 PR 状态和 head，若 head 或关键内容发生变化则重新检查并取得确认。
- 用户授权合并后，使用目标仓库允许的方式，并尽可能校验已审查的 head；同步本地分支前确认无冲突，优先快进，不覆盖本地改动。说明合并结果、本地同步状态及是否需要安装更新后的依赖。
