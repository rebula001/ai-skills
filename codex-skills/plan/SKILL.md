# 模块计划

帮助用户为**当前指定的一个模块**建立可执行、可修订的计划。计划的目标是让下一个交付切片可以可靠开始，而不是把整个项目或该模块的全部未来实现预先设计完。

## 边界与授权

- 调用 `$plan` 即授权创建或更新本次模块的计划 Markdown 文档，以及当前模块确实需要的共享技术基础或重大决策文档；如果用户明确说“只讨论，不写文档”，则不写入。实现文件、配置、依赖和外部系统仍须获得单独授权。
- 用户决定要定义哪些模块，以及本次要规划哪个模块。不要自行枚举、规划或展开其他模块；只记录当前模块已知的直接依赖和消费者。
- 对工作区、已有文档或获准工具中可可靠查到的事实自行调查；不要向用户索取本可自行查明的信息。
- 用户拥有目标、范围、优先级和产品取舍的最终决定权。给出建议，但不要把假设伪装成已确认决定。
- 模块的输入与输出先以业务能力、数据归属或服务契约描述；不要过早冻结 API、表结构、类结构或远期实现细节。
- 当前切片的阻塞问题解决后即可结束规划；延后项必须说明为何不阻塞当前切片及何时重审。需要先验证的阻塞问题应交付为“待验证”，不能标记为可开发。计划可随新事实修订。

## 选择当前模块

若用户尚未指定模块，先询问本次只规划哪个模块。模块一经选定，只建立该模块的决策树。

先阅读与该模块相关的现有代码、文档、约定和已确认的跨模块契约。若项目尚未有这些材料，则从用户提供的上下文开始；不要因此主动规划整个项目。

## 构建模块决策树

从模块目的开始，只展开会影响**当前交付切片**的决策。通常包括：

- 模块要解决的问题、服务对象和成功标准；
- 责任边界，以及明确不负责什么；
- 输入：用户动作、上游数据、事件或外部服务；
- 输出：用户可获得的结果、下游可使用的数据或能力；
- 数据与业务规则的归属；
- 已知依赖、消费者和最小跨模块契约；
- 当前交付切片、近期实施顺序、验收方式及其风险。

仅在会实质影响当前模块时，评估安全、权限、隐私、性能、可靠性、审计、无障碍、国际化和合规要求；记录最小可验证要求，或明确它不属于当前切片范围。

若当前切片改变已有持久化数据、公开契约或用户流程，明确兼容性、数据迁移、发布和回退方式。新模块可省略不适用的兼容与迁移内容；若当前切片包含首次部署，仍需说明最小发布检查和失败恢复方式。

若当前交付切片受共享技术选择约束，可讨论最小必要的技术基础：前后端语言与框架、数据库与迁移方式、部署/运行环境，以及确实阻塞当前工作的工具。不要因为“以后可能需要”而提前选择缓存、消息队列、微服务、监控平台或其他基础设施。

将每个问题分为三类：

- **现在决定**：会阻塞当前切片，或错误选择的返工成本很高；
- **先验证**：缺少事实，先定义一个有明确问题、最小验证方式、所需证据、退出条件与成本/范围上限的 Spike；
- **明确延后**：说明不阻塞当前切片的理由和复审触发条件；若采用可低成本调整的临时方案，明确该方案及其假设。

保持决策树在内部，除非展示它能帮助用户理解复杂关系。仍在调查的事实是未解决的前置条件，不能猜测。

## 分轮推进

采用**决策树与 frontier（前沿）**方法推进：将每项决定及其依赖关系组成内部决策树；frontier 是其前置条件已经明确、现在可以决定的一组问题。此方法已内置于本 skill，不依赖调用其他 skill。每一轮：

1. 简要报告已发现的事实与仍存在的假设。
2. 一次提出当前模块全部有价值的 frontier 问题；不要提出依赖于同一轮其他未决问题的问题。
3. 对每个问题说明它为何影响计划；必要时给出简短选项，并明确推荐答案。
4. 等待用户回答，然后重新计算下一轮 frontier。

一次提出整个 frontier；若问题过多而会妨碍用户判断，按紧密关联的主题拆成连续的小轮次，并说明拆分原因。不要把同一决定的依赖问题混在一轮中。

需要提问时使用以下格式：

```markdown
### 第 <n> 轮规划

**当前已知：** <相关事实与已确定选择>

1. **<决策项>** — <需要决定什么，以及其重要性>
   - 选项：<仅列出有意义的选项>
   - 建议：<推荐选项与简短理由>

2. **<决策项>** — <...>
   - 建议：<...>
```

若有充分依据的默认值风险很低且不改变结果，不必提问；将其列为假设即可。反之，只要猜测会改变范围、成本、用户体验、兼容性、安全性或可逆性，就应明确提出。

## 文档约定

项目已有的文档路径、命名和模板优先。没有约定时，采用以下默认结构：

```text
docs/planning/
├── README.md                       # 可选：已定义模块的索引
├── technical-foundation.md          # 可选：当前共享技术基础
├── modules/
│   └── <module>.md                 # 该模块持续维护的计划文档
└── decisions/
    └── D-<id>-<topic>.md           # 仅跨模块的重大决定
```

只在用户选择并开始规划某个模块后，创建该模块的文档。`README.md` 是可选索引，只列出已定义或正在规划的模块；不要预建未来模块的文件，也不要把它写成完整项目设计。

模块计划文档是该模块计划的唯一事实来源；独立决定文档应从相关模块文档链接，而不是复制内容。

## 共享技术基础

先读取并复用已确认的共享技术基线。当前模块需要新的共享技术选择，或用户已明确确认相关选择时，创建或更新 `docs/planning/technical-foundation.md`。模块文档链接到它，不重复内容。修改已有基线前，说明对已知模块和契约的影响，再由用户确认变更；不要借此展开其他模块的内部规划。

每项技术选择记录：当前选择、为什么现在必须决定、关键约束或原因，以及复审触发条件。文档可包含以下部分：

- 后端：语言、框架与运行时；
- 前端：语言、框架与必要的共享工具；
- 数据与持久化：数据库、迁移与备份责任；
- 部署与运行：环境、托管/服务器和 CI/CD；
- 明确延后：尚未阻塞当前模块的技术选择。

对 PostgreSQL 与 MySQL、Vue 与 React 这类会长期影响多个模块且需要保留完整取舍的选择，在 `docs/planning/decisions/` 建立独立决定记录，并从技术基础文档链接。

## 记录已确认决策

讨论中的观点不是正式决定。用户确认一批会影响后续工作的决定后，创建或更新 `docs/planning/modules/<module>.md`，或项目约定的位置。用户对具体问题的明确回答即为该决定的确认，无需重复审批；沉默、未回答的问题及 AI 建议仍不算确认。

每条已确认决策保留稳定的简短编号、决定和理由；必要时补充影响及复审条件。文档状态针对当前交付切片：讨论中、待验证、已确认可开发。个别决定已确认不代表整个切片已可开发。

文档应持续维护，并使用以下骨架。不适用的章节可省略；讨论中的内容可标记待确认，延后项保留理由和复审条件。不要为填满模板而提前决定。

```markdown
# <模块名称>

- 当前切片状态：讨论中 / 待验证 / 已确认可开发（选择其一）

## 模块目的与成功标准
## 当前范围与非目标
## 输入
## 输出
## 数据与规则归属
## 依赖与最小模块契约
## 当前交付切片
## 近期实施顺序
## 验收方式
## 非功能要求与风险（如适用）
## 兼容、迁移、发布与回退（如适用）
## 已确认决策
## 待验证假设
## 明确延后
## 变更记录
```

输入、输出和契约的每一项至少说明：来源或消费者、业务含义、拥有与维护方，以及当前交付切片是否需要它。不要将尚未确定的 API、表结构或内部实现伪装成契约。

“近期实施顺序”只列出完成当前切片所需的简短、有序步骤，帮助开发者从何处开始；不要拆分未来模块、远期切片或实现层级的琐碎任务。

小决定记录在模块计划文档的“已确认决策”中。只有跨模块、难以回退或长期影响架构、数据或部署的决定，才建立 `docs/planning/decisions/` 下的独立记录。决定被推翻时，在原计划中标记“已替代”，保留新决定和原因；不要无痕覆盖。不要为每一轮对话或每项实现细节创建文档。

## 文档自检与重新规划

写入或更新文档前，快速检查：

- 已确认决定、假设和待验证项是否被正确区分；
- 当前交付切片是否包含远期设计或与当前模块无关的工作；
- 输入、输出、数据/规则归属和模块契约之间是否矛盾或重复；
- 当前切片是否有可观察的验收方式；
- 适用的非功能要求是否有最小可验证标准；
- 对已有数据、契约或流程的变更是否已说明兼容、迁移、发布和回退；
- 每个 Spike 是否有最小验证方式、所需证据、退出条件和成本/范围上限；
- 阻塞当前切片的未知项是否明确列出，而非藏在 `TODO` 或含糊表述里；有标记的待确认、待验证和延后项可以保留。

若模块边界、契约、成功标准或范围变化，或 Spike 推翻关键假设，先确定受影响的决定、依赖和近期步骤。只暂停受影响工作，重开对应决策分支，保留仍有效的决定和可独立继续的工作。用户确认变更后，同步修订受影响的计划内容与近期步骤；若存在关联任务清单，标明失效项，避免执行旧任务。模块内部且不改变约定的普通实现调整无需重启规划。

## 完成当前模块计划

当前模块的 frontier 不必为空，但阻塞当前切片的问题必须已解决，且每个延后项都有不阻塞的理由。目标、范围、关键契约、近期步骤和验收方式明确后，汇总计划供用户确认；已确认的决定不重复询问，整体确认后标记“已确认可开发”。

若阻塞问题只能通过 Spike 验证，记录“待验证”状态、验证计划及其成本上限，下一步是验证；定义验证计划不等于验证完成，也不自动授权运行探针或开始业务实现。

计划完成不等于开始实现；除非用户明确要求，停在计划文档已更新、可供下一步开发使用的状态。
